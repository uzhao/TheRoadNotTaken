## What to build

知识网页顶部显示唯一一张推荐卡：待验证优先于学习中、学习中优先于未学、主干优先于分支、与最近主题同领域优先、后继多者优先、id 兜底；卡片写明命中的理由。学习者可「我已掌握」（变为声称掌握，推荐随即变成验证）、「其实没学过」（撤回）、「暂不学」（立即换下一个）、在看板上「恢复推荐」；分支领域有「纳入推荐」开关，默认关闭。每次状态写入经 schema 校验、临时文件原子替换，并以人可读信息提交 git。

## Acceptance criteria

- [x] 推荐算法为纯函数并通过 API 覆盖六级字典序的每一级（各一个构造状态的用例）
- [x] `claimed` 主题推荐为验证，`deferred` 不出现直到候选耗尽，分支开关关闭时分支主题不出现
- [x] 四个状态动作各自只改目标主题，`updated_at` 更新，`git log` 出现人可读提交
- [x] 候选为空且无暂不学时显示规格要求的提示
- [x] 写入过程中断不会留下损坏的 `state.json`（用临时文件 + 原子改名验证）

## Resolution

已实现：

- **推荐**：`backend/src/theroadnottaken/recommend.py` 是一个纯函数，按 013 的候选规则与六级字典序排序。理由取决于推荐主题与第二名在哪一级分出胜负。如果只有一个候选、或一直比到 id 才分出，就改用推荐主题自身最靠前的一条长处；没有长处时说「前置都已掌握，可以开始」。
  - 主干与分支分出胜负时，理由是「主干优先于分支」。
  - 「最近一次状态变化」只看学习中与已掌握的条目（即开始学习或验证通过）。暂不学和声称掌握不改变领域连续。
  - 暂不学的主题回归时，同样要求前置都已掌握。
  - 回归的卡片带 `was_deferred`，前端标「之前暂不学」。
  - 没有任何候选时（包括暂不学的主题全都不可学），返回规格的提示。
- **状态操作**：`actions.py` 定义四个操作，各自只能从规定的状态出发，否则返回 409 且不写入：
  - 我已掌握：未学、学习中、暂不学 → 声称掌握
  - 其实没学过：声称掌握 → 未学
  - 暂不学：未学、学习中 → 暂不学
  - 恢复推荐：暂不学 → 未学

  每个操作只改目标主题的 `status` 和 `updated_at`，薄弱点与验证记录保留。
- **写入**：`DataDir.update_state` 用锁把「读、改、写、提交」串成一步。`save_state` 写前按同一 schema 校验，先写同目录的临时文件并 fsync，再用 `os.replace` 替换。每次写入都提交 git，提交信息形如「我已掌握：函数极限与连续函数（c02-function-limit-continuity）未学 → 声称掌握」。
- **API**：
  - `GET /api/recommendation`
  - `POST /api/topics/{id}/{claim|unclaim|defer|restore}`
  - `PUT /api/fields/{id}/included`
  - `/api/fields` 的每一项新增 `included` 字段。
- **前端**：
  - 知识网页顶部有推荐卡。「开始学习」和「开始验证」暂时置灰，分别由 024 和 026 接入。
  - 看板卡片上有状态操作。
  - 侧栏每个分支领域有「纳入推荐」开关。

实施中做的决定（规格未写明）：

- 「纳入推荐」开关存在 `state.json` 的保留键 `included_branches` 里，与 `archived` 同一种做法，内容是开启的分支领域 id 列表，为空时不写出。它属于学习者状态，只有后端写。为它单开一个文件的话，数据目录布局要改，不值得。
- 「恢复推荐」和「其实没学过」都把主题回到「未学」，与原型 010 一致，不记录之前的状态。所以「学习中 → 暂不学 → 恢复」之后，这个主题不再享有「上次没学完」的排序优先，但薄弱点与验证记录不丢。

测试在 `backend/tests/test_recommendation.py` 和 `test_state_actions.py`：六级排序每一级各一个用例，并逐级做过变异检查（删掉某一级的排序键，对应用例就失败）；四个操作各有用例，覆盖只改目标、`updated_at` 更新和 git 提交；另有非法转移、开关持久化，以及在原子改名前中断写入的用例。
